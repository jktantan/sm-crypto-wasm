# Производительность

Горячие участки (модульная арифметика больших чисел, компрессия хеша, раунды блочного
шифра, билинейные спаривания) выполняются внутри WASM. Таблица покрывает **каждую публичную
операцию**; столбец `gmkitx` — эталон на чистом JS на той же машине, с теми же параметрами
и сообщениями (**операций, которых там нет, помечены `—`**). Измерено на AMD Ryzen 7
7800X3D / Node 24.15 / Windows 11; воспроизводится через `pnpm bench`.

## Очное сравнение с двумя другими библиотеками

Выше эталон — чистый JS `gmkitx`. Если взять **две другие реальные библиотеки китайской
криптографии**, с теми же параметрами, сообщениями и ключами:

- **Cubelrti/sm-crypto-wasm** — Rust + `wasm-bindgen`, скомпилированный в WebAssembly
  (⚠️ имя пакета совпадает с этим проектом, но код другой);
- **sm-crypto-v2** — TypeScript + [noble-curves](https://github.com/paulmillr/noble-curves),
  один из самых быстрых вариантов на чистом JS.

Каждая сторона — это **release-сборка из своих исходников**; в бенчмарк встроена
самопроверка, побайтово сравнивающая выводы всех трёх (SM3 / SM4 обязаны совпадать,
перекрёстная проверка подписи SM2 обязана проходить) — при расхождении выбрасывается
ошибка, а не «красивое» число.

```bash
bash bench/build-cubelrti-wasm.sh   # создаёт bench/.vendor/cubelrti/pkg/
pnpm bench:cubelrti
```

::: details Три наблюдения
- **Rust→WASM не обязательно быстрее**: SM2 у Cubelrti проигрывает *чистому JS*
  `sm-crypto-v2` по всем операциям (подпись — в 15× медленнее). Его горячий путь использует
  `num-bigint` (универсальные большие числа с выделением в куче) вместо арифметики
  фиксированной ширины; каждый вызов API заново выводит открытый ключ (его `keypair` —
  2.20 ms, примерно половина `sign` — 4.56 ms, то есть в подписи выполняется два скалярных
  умножения); к тому же каждая экспортируемая функция вызывает `console::log_1`.
- **`sm-crypto-v2` — потолок чистого JS**: на SM4 он примерно наравне с Cubelrti, а на SM3
  отстаёт от этого проекта всего в 1.35×.
- **Для массовых подписей есть отдельный путь**: `sm2.createSignaturePointPool(n)`
  амортизирует умножение на базовую точку (56% времени подписи) заранее, снижая одну
  подпись с 141 µs до **24 µs (в 5.9×)** при попадании в пул.
:::

## Почему так

- **SM3 получил ещё один раунд**: `compress` раньше материализовал W′ (`W[j] ^ W[j+4]`)
  отдельным проходом из 64 записей + 128 чтений; теперь это вычисляется на месте внутри
  цикла раундов. Циклы раундов используют инкремент указателей, а буфер дополнения
  переиспользуется на уровне модуля (раньше каждый вызов `hash` делал
  `new StaticArray<u8>(totalLen)` и **обнулял всю длину**, тогда как обнулять нужно только
  область padding). **HMAC целиком перенесён в WASM** (склейка ipad/opad и два вызова
  хеширования раньше происходили в JS: четыре перехода через границу плюс три временных
  массива), для чего добавлен вход с двумя сегментами, позволяющий `ipad ‖ msg` попадать
  прямо в дополнение. Итог: hash быстрее на **26%**, hmac — на **45%**.
- **SM4 / ZUC упираются в S-бокс**: оба ограничены **табличным 8-битным S-боксом**, а
  WebAssembly не предоставляет ни ARMv8 `SM4E`, ни AES-NI. SM4 пробовал `v128` SIMD — вышло
  *медленнее* 8-кратного скалярного чередования (четыре независимые цепочки зависимостей
  на блок, скрывающие задержку L1 за счёт внеочередного исполнения); этот путь удалён.
  SM3 же — цепочка MD (блоки нельзя распараллелить) с последовательной компрессией в 64 раунда.
- **CFB / OFB в SM4 когда-то были медленнее чистого JS**: эти режимы вызывали wasm поблочно
  (64 перехода на 1 КБ). Пакетные экспорты снизили их до ~10 µs, то есть в 3.6~3.8× быстрее.
- **Вычислительный слой SM2 прошёл восемь этапов работы** (редукция Солинаса, возведение в
  квадрат по Комба, comb/wNAF скалярное умножение, вычисления на точках на месте, смешанные
  координаты, совместное скалярное умножение при проверке, инверсия на уровне слов, кеш
  вывода открытого ключа для `sign`). Подробности — в
  [`docs/performance-ceiling.md`](https://github.com/jktantan/sm-crypto-wasm/blob/main/docs/performance-ceiling.md).
- **SM9 определяется спариваниями.** Переход базового поля в домен Монтгомери (CIOS) снизил
  одно модульное умножение с 179 нс до 98 нс и ускорил все сквозные операции в **1.6~1.8×**.
  Сопоставимой реализации SM9 на чистом JS нет, поэтому даны только абсолютные значения.
- **hex-кодеки важны**: переход на `Buffer.toString('hex')` (с табличным запасным вариантом
  в браузерах) ускорил кодирование примерно в 27×; на входе проверка и разбор объединены в
  один проход. Вместе это ускорило SM3 / SM4 / ZUC с hex-входом на **27~32%**.
