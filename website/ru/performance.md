# Производительность

Горячие участки (модульная арифметика больших чисел, компрессия хеша, раунды блочного
шифра, билинейные спаривания) выполняются внутри WASM. Таблица покрывает **каждую публичную
операцию**; столбец `gmkitx` — эталон на чистом JS на той же машине, с теми же параметрами
и сообщениями (**операций, которых там нет, помечены `—`**). Измерено на AMD Ryzen 7
7800X3D / Node 24.15 / Windows 11; воспроизводится через `pnpm bench`.

## Почему так

- **SM3 / SM4 / ZUC у потолка.** SM3 — цепочка MD (блоки нельзя распараллелить) с
  последовательной 64-раундовой компрессией; SM4 и ZUC упираются в **таблицу 8-битных
  S-box**, а WebAssembly не предоставляет ни `SM4E` из ARMv8, ни AES-NI.
- **CFB / OFB у SM4 раньше были медленнее чистого JS** — вызовы в wasm поблочно (64 перехода
  на КБ). Пакетные экспорты дали ~10 µs, то есть в 3.6~3.8× быстрее.
- **SM9 определяется спариванием.** Перевод базового поля в домен Монтгомери (CIOS) снизил
  одно модульное умножение с 179 до 98 нс и ускорил все сквозные операции в **1.6~1.8×**.
- **Кодеки hex имели значение**: переход на `Buffer.toString('hex')` (с табличным
  фолбэком в браузере) дал ~27×; валидация и разбор ввода объединены в один проход.
  Вместе это ускорило SM3 / SM4 / ZUC с hex-вводом на **27~32%**.
